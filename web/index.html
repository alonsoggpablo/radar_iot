Radar IoT

Integración del sensor uRAD Smart Traffic RPi (radar 60 GHz FMCW con Raspberry Pi embebida, fabricado por Anteral) en la plataforma IoT de AGlabs: del dispositivo en columna al dashboard de Boreas, con cliente MQTT corriendo directamente en la RPi del propio sensor.

DispositivouRAD Smart Traffic RPi · 60 GHz FMCW · IP66
Alcance30 m (conteo) · 100 m (otras apps) · ≤ 180 km/h
CómputoRaspberry Pi embebida · Linux · Python
BackhaulWiFi + 4G (dongle opcional) · MQTT/TLS

01Arquitectura general

El Smart Traffic RPi es una solución integrada: en una sola caja IP66 conviven el radar uRAD Industrial 60 GHz, una Raspberry Pi (Quad-core ARM, 2 GB RAM, Linux) y un dongle 4G opcional. La RPi ejecuta el software de conteo en Python y, en nuestra integración AGlabs, hará también de cliente MQTT publicando contra mqtt.aglabs.es. No hace falta bridge externo.

  • Nivel 1 — un único dispositivo en columna. La Raspberry Pi embebida es el "bridge": consume el flujo UART del radar y publica MQTT contra el broker. No hay caja anexa, ni ESP32, ni transceiver RS-485.
  • Nivel 2 — broker MQTT corporativo (mqtt.aglabs.es) ya operativo. Cero infraestructura nueva de mensajería.
  • Nivel 3 — ingesta en TimescaleDB con el mismo patrón que nexus_electrical / nexus_iaq; visualización embebida en Boreas como una capa más.
  • El backhaul es WiFi o 4G, decidido por emplazamiento. Si hay WiFi del mobiliario urbano disponible, basta; si no, el dongle 4G interno mantiene la conectividad.

Capacidades del firmware

  • Conteo bidireccional simultáneo: velocidad positiva (alejándose) y negativa (acercándose) en la misma medida.
  • Clasificación de objetivos: 1 = vehículo normal (< 8 m), 2 = medio (8–15 m), 3 = largo (> 15 m), 4 = bicicleta/motocicleta, 5 = peatón (< 10 km/h).
  • Dos modos de operación: HIGHWAY_SCENARIO=True (autopistas, ≥ 120 km/h, mayor velocidad / menor resolución, sin clasificar bicis ni peatones) y HIGHWAY_SCENARIO=False (urbano/interurbano, mejor resolución y clasificación).
  • Plataforma web del fabricante opcional para visualización en tiempo real e informes descargables (alternativa a la integración AGlabs nativa).

03Software embebido y publicación a MQTT

La RPi viene con el programa principal vehicleCounter_smartcities_v2_x.py en ~/Desktop/uRAD_Tracking_v2_x/ y un servicio pm2 llamado radar para arranque automático. La integración AGlabs consistirá en añadir un wrapper Python que tail-ee el fichero de salida (o invoque directamente la API del firmware) y publique los eventos al broker.

Parámetros de configuración del firmware

### MODE SELECTION ###
HIGHWAY_SCENARIO = True   # False para urbano (< 120 km/h)

#### COMMUNICATION INTERFACE ####
USB_COMMUNICATION = False
USE_FAN = True            # ventilador PWM en pin 12

#### CONFIGURATION PARAMETERS ####
USB_CONNECTOR_UPWARD = False
pitch_angle = 15          # inclinación con la vertical (grados)
yaw_angle   = 0           # apuntamiento horizontal · ver §04

VELOCITY_POSITIVE = True   # contar vehículos alejándose
VELOCITY_NEGATIVE = True   # contar vehículos acercándose

X_MINIMUM_NEGATIVE_VELOCITY = -7.5
X_MAXIMUM_NEGATIVE_VELOCITY = -0.5
X_MINIMUM_POSITIVE_VELOCITY =  0.5
X_MAXIMUM_POSITIVE_VELOCITY =  7.5

#### OUTPUT RESULTS ####
SAVE_RESULTS = True
SAVE_RAW_DATA = False     # nube de puntos 3D — solo debug
OUTPUT_DATE_TIME_FORMAT = 1 # 0=ISO, 1=UNIX timestamp
FOLDERNAME = 'Results'
OUTPUT_FILENAME = 'Vehicle_results.txt'

Formato de salida — Vehicle_results.txt

Cada línea = un vehículo detectado. Cuatro columnas separadas por espacio/tab:

CampoSignificado
timestampFecha/hora ISO (yyyy/mm/dd HH:MM:SS) o UNIX según OUTPUT_DATE_TIME_FORMAT
velocitykm/h · positivo = alejándose · negativo = acercándose
x_distancemetros · distancia horizontal del vehículo (útil para identificar carril)
type1=normal · 2=medio · 3=largo · 4=bici/moto · 5=peatón

Servicio pm2 (autostart)

# gestión del servicio "radar" ya instalado de fábrica
pm2 list                  # estado actual
pm2 start radar           # lanza vehicleCounter_smartcities_v2_x.py
pm2 stop  radar
pm2 save                  # persiste estado actual
pm2 startup               # habilita arranque al boot · ejecutar la línea sudo env... que devuelve

Plan de publicación MQTT (AGlabs)

Topics propuestos para el broker mqtt.aglabs.es (idénticos al planteamiento original, agnósticos al hardware):

aglabs/radar/<site>/<sensor>/track     # cada vehículo: velocidad, distancia, id, tipo
aglabs/radar/<site>/<sensor>/event     # cruces de umbral, alarmas
aglabs/radar/<site>/<sensor>/state     # configuración activa, app cargada
aglabs/radar/<site>/<sensor>/$health   # LWT + heartbeat
  • Payload JSON con timestamp ISO 8601 UTC, velocity_kmh, x_m, type, id, sensor_id, site.
  • Cliente Python con paho-mqtt, TLS al puerto 8883 del broker, ACL por client_id (ya implementado en aglabs_mqtt).
  • Wrapper como servicio pm2 adicional (aglabs_mqtt_bridge) que tail-ee Vehicle_results.txt y publica; convive con el servicio radar de fábrica sin tocarlo.
  • QoS 1 + buffer local (cola SQLite o equivalente) ante caída de red — la red puede caerse, el conteo no debe perderse.

04Instalación y montaje

El rendimiento del sensor depende fuertemente de la geometría de instalación. Estas son las recomendaciones del manual del fabricante (versión 28/10/2025) que aplican a todo despliegue AGlabs.

Altura e inclinación

El radar debe colocarse a una altura ≥ 3 m e inclinarse hacia el suelo según fórmula tilt = atan(height / 15). Tabla de referencia:

AlturaInclinación (pitch)
3 m11 °
4 m15 °
5 m18 °
6 m22 °

Ángulo de guiñada (yaw) según carriles

CasoYaw recomendado
1 carril a un lado del radar0 °
2 carriles a un lado15 °
3 carriles a un lado30 °

Convención de signo: radar a la izquierda de la calzada → yaw > 0. Radar a la derecha de la calzada → yaw < 0. Para 6 carriles totales (3+3), se recomiendan dos radares (uno por sentido) — la precisión cae más allá de ± 8 m laterales.

Otras reglas de instalación

  • Conector hacia abajo: el dispositivo debe montarse con el prensaestopas hacia el suelo.
  • Tramo recto: instalar en una sección recta de carretera a lo largo de la distancia de detección (0–25 m). Evitar curvas.
  • Sin paradas: instalar donde los vehículos no se detengan completamente — un coche parado puede generar conteos duplicados al reanudar marcha.
  • Anclaje: el kit incluye soporte para columna cilíndrica con articulación central (tornillo de ajuste vertical) y abrazaderas.
  • Provisión WiFi inicial: para configurar/operar en campo, crear un AP móvil con SSID uRAD_SN**** (las cuatro cifras y la clave se entregan con el dispositivo); la RPi se asocia automáticamente y se accede por SSH o VNC.
Bandera ISM 60 GHz: banda exenta en EU (CE bajo certificado examen de tipo EU n.º 803416897303). No requiere licencia ni tasas municipales para uso de espectro.
Marcado: RED Art. 3.1(a) seguridad (EN 62368-1, EN 62311), 3.1(b) EMC (EN 301 489-3), 3.2 espectro (EN 305 550-2), RoHS (EN 63000).

05Casos de uso en la plataforma AGlabs

Líneas de uso prioritarias para el portfolio AGlabs (clientes municipales, RG, gestión de carriles bici, movilidad urbana). El firmware del Smart Traffic RPi cubre todas con la misma configuración base — varían los parámetros X_*, yaw_angle y los filtros aguas abajo en Boreas.

Radar pedagógico y control de velocidad

Medida en tiempo real de velocidad y distancia de vehículos en ambos sentidos. Activación de panel luminoso reactivo por umbral configurable (publicado vía MQTT). Histórico en TimescaleDB para auditoría y comparación temporal.

Aforo multicarril de tráfico para municipios

Velocidad, dirección, distancia horizontal (carril) y tipo por vehículo en hasta 4 carriles simultáneos. Dashboard en Boreas por concejo: intensidad horaria, IMD, velocidades medias y percentiles, mapa de calor por punto de medida.

RG · gestor_concejoDatos abiertos potenciales

Aforo de bicicletas en carril bici

Modo urbano (HIGHWAY_SCENARIO=False) para que el clasificador distinga bicis (tipo 4) y peatones (tipo 5). Indicador de uso del carril bici para políticas municipales de movilidad sostenible.

Movilidad sostenibleIndicadores municipales

Detección y conteo de peatones

Objetivos con velocidad < 10 km/h se clasifican automáticamente como peatones. Útil en pasos de cebra, plazas, accesos a centros municipales. Compatible con triggers de señalización lumínica (panel LED) a través de un panel auxiliar reactivo al MQTT.

Pasos de peatonesAccesibilidad

Los cuatro casos comparten infraestructura: mismo dispositivo, misma RPi, mismo broker MQTT, misma hypertable. La diferencia entre despliegues es la configuración del firmware (modo highway/urbano, ángulos, ventanas X) y los filtros / paneles de Boreas. No hay diferenciación física por caso de uso.
